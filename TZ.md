# Веб видео-приложение для звонков peer to peer

## Суть

Одностраничное веб-приложение для видеозвонков между двумя участниками напрямую. Весь трафик шифруется сквозным шифрованием. Хостинг страницы — GitHub Pages, статика.

Приложение работает в двух режимах, и первый — основной:

**Режим 1, без сервера (по умолчанию).** Участники обмениваются кодами подключения вручную — копипастом или QR. Никакой серверной части не задействовано вообще. Покрывает большинство сетей.

**Режим 2, со своим сервером.** Включается, только когда прямое соединение не удалось (symmetric NAT, зарезанный UDP). Пользователь разворачивает свой сервер одной командой и указывает его адрес в настройках. После этого ручной обмен кодами не нужен: подключение идёт по ссылке. Сервер лежит в этом же репозитории, разворачивается через Docker.

Переход во второй режим — осознанное решение пользователя, а не автоматическая деградация. Приложение сначала честно пытается обойтись без сервера (см. 1.2) и только затем предлагает его завести.

## Ограничения платформы

- Страница — полностью статический сайт без бэкенда.
- Работает на десктопе и на мобильных (Chrome, Safari, Firefox, Edge актуальных версий).
- HTTPS обязателен (требование `getUserMedia`) — GitHub Pages его даёт.
- Сигнальный сервер, если он используется, обязан быть за `wss://`: иначе браузер заблокирует соединение как mixed content. Исключение — `ws://localhost` для разработки.

## 1. Установка соединения

### 1.1 Сигналинг — ручной обмен кодами

Сервера сигналинга нет, его роль выполняет пользователь.

1. Инициатор нажимает «Создать звонок» → `createOffer()` → ожидание **полного сбора ICE-кандидатов** (non-trickle) с таймаутом 5 секунд, чтобы зависший STUN не блокировал процесс.
2. SDP сериализуется компактно: из него извлекаются только значимые поля (ice-ufrag, ice-pwd, DTLS fingerprint, список кандидатов, кодеки, публичный ECDH-ключ) → бинарная упаковка → `CompressionStream('deflate-raw')` → base64url. Целевой размер кода — **до ~800 символов**.
3. Код передаётся собеседнику любым каналом. Поддерживаются два способа: копирование текста и QR-код (генерация + чтение камерой через `BarcodeDetector` с фолбэком на jsQR).
4. Второй участник вставляет код, получает ответный код, отправляет обратно. `setRemoteDescription` → соединение установлено.

После установки соединения открывается DataChannel — через него идут служебные команды (смена качества, ротация ключей, ICE restart), повторный ручной обмен для этого не нужен.

### 1.2 Стратегия соединения: делаем всё, чтобы обойтись без TURN

ICE перебирает пути сам, наша задача — не мешать и максимально расширить набор вариантов. Порядок, в котором соединение может состояться:

| Приоритет | Путь | Когда работает |
|---|---|---|
| 1 | **host IPv6** | У обоих есть IPv6 — NAT отсутствует как явление, соединение прямое |
| 2 | **host IPv4 (mDNS)** | Оба в одной локальной сети |
| 3 | **srflx через STUN** | Большинство домашних NAT — классический hole punching |
| 4 | **prflx** | Спасает случай «symmetric NAT с одной стороны + cone с другой», ICE делает это автоматически |
| 5 | **relay через TURN** | Только если пользователь развернул свой сервер |

Что делаем активно:

- **Список из нескольких STUN-серверов** разных операторов, включая dual-stack — увеличивает шанс собрать полный набор кандидатов и нужен для диагностики (см. ниже).
- `iceCandidatePoolSize` для предварительного прогрева кандидатов до нажатия кнопки.
- Не фильтруем типы кандидатов, не ограничиваем транспорт.
- **Пре-флайт диагностика NAT**: до обмена кодами поднимаем `RTCPeerConnection` с двумя разными STUN-серверами и сравниваем внешние порты в srflx-кандидатах. Порты различаются → у пользователя symmetric NAT → предупреждаем **заранее**, а не после впустую потраченного обмена кодами. Сравнивать можно только пробы с общим базовым адресом: разные локальные сокеты законно получают разные внешние порты и на обычном NAT.
- При `iceConnectionState === 'failed'` — один автоматический **ICE restart** через DataChannel или, если он не поднялся, повторный сбор кандидатов: NAT-маппинги могли смениться, иногда со второй попытки встаёт.
- Диагностика через `getStats()`: определяем тип выбранной пары кандидатов и показываем пользователю, идёт ли соединение напрямую или через ретранслятор.

Известное ограничение: если один участник только на IPv6, а другой только на IPv4, прямое соединение невозможно — нужен dual-stack TURN.

### 1.3 Поведение при провале соединения

Если все пути исчерпаны и сервер не настроен — честное сообщение вместо бесконечного «соединение…»:

> Не удалось установить прямое соединение. Ваша сеть (или сеть собеседника) использует тип NAT, который невозможно обойти без сервера-ретранслятора.
>
> Что можно попробовать:
> - переключиться с мобильного интернета на Wi-Fi;
> - отключить VPN;
> - развернуть свой сервер — достаточно одному из вас.

Рядом — ссылка на `DEPLOY.md` и оценка: сервер нужен примерно в 10–20% случаев, а на мобильном интернете чаще.

### 1.4 Режим со своим сервером: подключение по ссылке

Когда в настройках указан адрес сигналинга (`wss://<домен>/ws`), ручной обмен кодами отключается. Вместо него:

1. Инициатор нажимает «Создать ссылку». Клиент генерирует **идентификатор комнаты** (16 случайных байт) и **секрет комнаты** (32 случайных байта).
2. Ссылка вида `https://user.github.io/p2p-call/#j=<приглашение>` отправляется собеседнику. Приглашение содержит адрес сервера, идентификатор комнаты и секрет.
3. Оба клиента подключаются к серверу по websocket, входят в комнату и обмениваются SDP через неё. Ручного копирования больше нет — как только второй открыл ссылку, соединение устанавливается само.
4. Сервер выдаёт временные учётные данные TURN (HMAC-токены со сроком годности), поэтому общий секрет coturn клиенту не попадает.

**Ключевое свойство: всё содержательное лежит во фрагменте ссылки, после `#`.** Фрагмент по устройству HTTP не уходит на сервер — ни в запросе, ни в `Referer`. Секрет комнаты остаётся только в браузерах участников, и на этом держатся два уровня защиты:

- **Сигналинг запечатан.** SDP шифруется AES-256-GCM на ключе, выведенном из секрета комнаты. Сервер видит идентификатор комнаты и непрозрачный блоб. Подменить DTLS-fingerprint и сесть в середину он не может — классическая слабость WebRTC-сервисов здесь закрыта.
- **Медиаключи зависят от того же секрета.** Даже если сигналинг вскрыть, сквозной слой шифрования кадров сервер не обходит.

Что сервер всё-таки видит: IP-адреса участников, время звонка, идентификатор комнаты, а при ретрансляции — объём и тайминги трафика. Это неустранимо и должно быть написано в интерфейсе.

Ограничения режима: комната строго на двоих (третьему приходит `room-full`), опустевшая комната живёт ещё 10 минут на случай перезагрузки вкладки, размер блоба ограничен, частота сообщений ограничена токен-бакетом.

### 1.5 Серверная часть в репозитории

Лежит в `server/`, разворачивается одной командой `docker compose up -d` после заполнения трёх значений в `.env`. Подробности — в `DEPLOY.md`.

Состав: **caddy** (TLS от Let's Encrypt, обратный прокси), **signaling** (Node + ws, ретрансляция блобов и выдача TURN-кредов), **coturn** (ретранслятор медиа).

Требования к серверной части:

- Никакого хранения: комнаты живут в памяти, содержимое сообщений не разбирается и не логируется.
- Файл протокола сигналинга общий с фронтендом — проверка входящих сообщений должна быть ровно одна на обе стороны, а не две расходящиеся копии.
- Падать на старте с внятным сообщением при противоречивой конфигурации, а не обнаруживать это в момент несостоявшегося звонка.
- coturn запрещает ретрансляцию в приватные диапазоны адресов — иначе сервер превращается в прокси во внутреннюю сеть хостера.
- Процесс не под root.

## 2. Шифрование

Шифрование **всегда включено и не отключается**. Выбора уровня нет: пользователю не предлагается делать себе хуже. Замеры показывают, что AES-GCM в WebCrypto идёт через аппаратный AES-NI и на потоке 2 Мбит/с стоит доли процента CPU — экономить тут не на чем.

### 2.1 Слой 1 — транспортный (встроенный в WebRTC)

DTLS-SRTP, отключить невозможно в принципе:

- DTLS 1.2/1.3 хендшейк, обмен ключами **ECDHE P-256** (forward secrecy).
- SRTP профиль `AEAD_AES_256_GCM` / `AEAD_AES_128_GCM`.
- DataChannel (SCTP поверх DTLS) шифруется той же сессией.

Поскольку SDP с DTLS-fingerprint передаётся из рук в руки, а не через сервер, этот слой сам по себе уже даёт настоящий E2EE — сервера, способного подменить fingerprint, в схеме просто нет.

### 2.2 Слой 2 — сквозное шифрование кадров

Реализуется через `RTCRtpScriptTransform` (фолбэк на `createEncodedStreams()` в старых Chrome), шифрование в воркере.

**Согласование ключей:**
- ECDH P-256, публичные ключи едут в кодах подключения.
- Опционально — **общая парольная фраза**, согласованная участниками заранее и отдельным каналом. Через PBKDF2 подмешивается в общий секрет. Это главная практическая ценность второго слоя: защищает даже если канал обмена кодами скомпрометирован.
- HKDF-SHA-256 выводит независимые ключи на каждое направление и на каждый тип медиа.

**Шифрование кадра:**
- **AES-256-GCM**.
- Nonce 12 байт, строится детерминированно: `4 байта id потока + 8 байт монотонный счётчик кадров`. Никогда не случайный — повтор nonce в GCM катастрофичен.
- Заголовок кодека остаётся открытым (Opus — 1 байт, VP8 — 3/10 байт, H.264 — по структуре NAL), но передаётся в `additionalData` AES-GCM, то есть **аутентифицируется**: незаметно подменить его нельзя.
- Трейлер 1 байт с id ключа — позволяет ротировать ключи посреди звонка без рассинхрона.
- **Ротация ключей раз в 30 секунд** через HKDF-цепочку (forward secrecy внутри звонка).

**Деградация:** если браузер одного из участников не поддерживает Encoded Transform, звонок не блокируется, но работает только на слое 1, и в интерфейсе висит явное заметное предупреждение. Это не пользовательская настройка, а реакция на возможности платформы.

### 2.3 Защита от MITM — SAS

Из общего ECDH-секрета и обоих DTLS-fingerprint через HKDF выводится 40 бит, отображаемых как **5 слов** из словаря на 256 слов. Участники сверяют их голосом по уже установленной связи.

Требования к словарю:

- **Не локализуется.** Обе стороны обязаны увидеть одну и ту же фразу; если словарь поедет за языком интерфейса, собеседники с разными языками увидят разные слова и решат, что их слушают. Язык словаря — английский как наиболее вероятно произносимый и узнаваемый обеими сторонами.
- **Фонетическая различимость.** Сверка идёт голосом и часто на плохой линии, поэтому в списке не должно быть омофонов (kernel/colonel) и пар, различающихся одним звуком (amber/ember, berry/ferry). Последнее проверяется тестом автоматически.
- **Смена списка — смена версии протокола**: стороны на разных версиях увидят разные фразы.

Злоумышленник, подменивший коды, вынужден держать две разные сессии с разными общими секретами — SAS у сторон не совпадёт, а подделать голос собеседника в реальном времени он не может.

### 2.4 Что шифрование не скрывает

RTP-заголовки, размеры пакетов, тайминги. При прямом P2P это неважно — наблюдателя в канале нет. При использовании TURN ретранслятор видит эти метаданные, но не содержимое. Указать в интерфейсе при работе через relay.

## 3. Медиа

- **Качество видео**: пресеты 360p / 720p / 1080p / авто. Реализация — `getUserMedia` constraints + `sender.setParameters({encodings: [{maxBitrate, scaleResolutionDownBy, maxFramerate}]})`. Меняется на лету, ренеготиация не требуется. Выбор синхронизируется с собеседником через DataChannel (уведомление, не принуждение).
- **Микрофон и камера**: включение/выключение через `track.enabled`, мгновенно. Состояние собеседника отображается — передаётся по DataChannel.
- **Подключение без своих устройств.** Отсутствие камеры и микрофона не должно мешать войти в звонок: участник подключается на просмотр и слушает. Требования к реализации:
  - `getUserMedia` атомарен — запрос видео и звука разом падает целиком, если нет чего-то одного. Поэтому при неудаче нужно спускаться по лестнице: снять привязку к сохранённому устройству (его могли отключить, а id указан как `exact`), затем пробовать каждый вид отдельно.
  - Без собственной дорожки m-строка в SDP не появится, и встречный поток не придёт. Для каждого недостающего вида добавляется `recvonly`-трансивер.
  - Кнопки, за которыми нет дорожки, гасятся: живая кнопка «Микрофон», которая ничего не делает, — обман.
  - Причины различаются в сообщениях: «нет устройства», «устройство занято», «отказано в доступе» и «выбранное устройство отключено» требуют от пользователя разных действий. К сообщению добавляется перепись того, что видит браузер.
- **Выбор устройств**: список камер и микрофонов, переключение во время звонка.
- Индикаторы: битрейт, потери пакетов, RTT, тип соединения (прямое / через ретранслятор) — из `getStats()`.

## 4. Платформенные требования

- iOS Safari: `playsinline` обязателен, автовоспроизведение только с `muted`, `getUserMedia` доступен только в Safari-движке.
- Мобильный UX: обмен кодами по умолчанию через QR, копипаст как альтернатива.
- Адаптивная вёрстка, вертикальная и горизонтальная ориентация.

## 5. Явно вне скоупа

- Более двух участников (ручной сигналинг этого не позволяет).
- История звонков, аккаунты, контакты.
- Запись звонка.
- Демонстрация экрана (кандидат на вторую итерацию).
- Автоматическое переподключение после полного обрыва соединения в режиме без сервера — потребуется новый обмен кодами. В режиме со ссылкой переподключение по той же ссылке работает, пока жива комната.
- Хостинг сервера как услуга: сервер разворачивает пользователь у себя, публичного инстанса проекта нет.
